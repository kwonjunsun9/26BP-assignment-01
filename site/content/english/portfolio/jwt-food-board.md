## 프로젝트 소개

**배부르면 행복합니다!**는 식당 이름과 위치, 방문 후기를 제목과 본문에 담아 공유하는 맛집 게시판입니다. 누구나 게시글 목록과 상세 내용을 읽을 수 있고, 로그인한 사용자는 글을 작성하며 본인이 쓴 글만 수정·삭제할 수 있습니다.

Vue 화면과 Express API 서버를 JavaScript로 연결하고, SQLite 파일에 게시글을 저장했습니다. 이 프로젝트에서는 **서버가 검증한 사용자만 신뢰하고, 화면과 API 양쪽에서 인증 상태와 작성자 권한을 일관되게 처리하는 것**에 집중했습니다.

| --- | --- | --- |
| 개인 프로젝트 · 1명 | 2026.10 | Vue 3, Node.js, Express, JWT, SQLite(sql.js), Vite |

## 직접 구현한 범위

수업에서 제공한 기본 CRUD 라우트, 계정의 비밀번호 검증과 SQLite 저장 구조를 활용했습니다. 미완성이었던 로그인과 JWT 발급·검증, 프론트엔드의 인증 연결과 작성자 권한 검사를 완성하고 입력·오류 처리를 보완했습니다.

- 정상 계정의 로그인 응답에 JWT와 공개 사용자 정보를 반환하는 처리
- Bearer 토큰의 서명·만료·클레임 검증과 실제 사용자 확인
- 인증된 사용자와 DB의 작성자 정보를 비교하는 수정·삭제 권한 검사
- 브라우저 메모리에 토큰을 저장하고 보호 요청에 인증 헤더를 보내는 처리
- 401과 403을 구분한 세션 관리와 원인별 화면 안내
- 허용 필드·문자열 길이 검사, 로그아웃 시 입력 초기화와 없는 글의 화면 정리

## 서비스 구조와 요청 흐름

```text
Vue 화면 → Vite의 /api 프록시 → Express API → SQLite 파일
   ↑                              ↓
   └────────── JSON 응답 ──────────┘
```

로그인 시 `POST /api/auth/login`으로 이메일과 비밀번호를 전송합니다. 서버는 입력과 계정을 확인한 뒤 `issueToken()`으로 JWT를 발급하고, 브라우저는 응답의 `accessToken`과 `user`를 메모리에 보관합니다.

글 수정 시에는 `PUT /api/posts/{id}`에 `Authorization: Bearer <JWT>` 헤더를 보냅니다. 서버는 **토큰 검증 → 게시글 조회 → 작성자 비교 → 입력 검증 → DB 변경** 순서로 처리합니다. 인증이나 권한 검사에 실패하면 기존 데이터를 변경하지 않습니다.

| 파일 | 담당하는 기능 |
| --- | --- |
| `backend-express/src/auth.js` | JWT 발급, 토큰 검증, 작성자 권한 검사 |
| `backend-express/src/app.js` | 로그인·게시글 API, 입력 검사와 공통 오류 응답 |
| `frontend-vue/src/api.js` | 메모리 세션, Bearer 헤더 전송과 401 응답 처리 |
| `frontend-vue/src/App.vue` | 로그인 상태 표시, 글 작성·수정·삭제와 오류 안내 |
| `backend-express/src/store.js` | 제공 코드의 SQLite 파일 저장과 데이터 유지 |

## 핵심 설계

### 토큰을 읽는 것과 검증하는 것 구분하기

JWT 내용을 읽는 것만으로 사용자를 신뢰할 수는 없습니다. `currentUserId()`에서 `jwt.verify()`를 사용해 HS256 알고리즘, 서명, 만료, 발급자와 사용 대상을 검증했습니다. 이어서 필수 클레임인 `exp`와 `sub`의 형식을 확인하고, 해당 사용자가 실제 계정에 존재하는지도 검사했습니다.

토큰 누락은 `TOKEN_REQUIRED`, 변조 등 유효하지 않은 토큰은 `INVALID_TOKEN`, 정상 서명의 만료 토큰은 `TOKEN_EXPIRED`로 구분했습니다. 보호 API의 401 응답에는 `WWW-Authenticate: Bearer` 헤더를 포함했습니다.

### 작성자 권한을 서버에서 판단하기

화면에서 타인의 수정·삭제 버튼을 숨겨도 직접 API 요청을 보낼 수 있습니다. `assertOwner()`에서 인증된 사용자 ID와 DB에 저장된 게시글 작성자 ID를 비교하고, 다르면 DB 변경 전에 `403 FORBIDDEN`을 반환하도록 했습니다.

글 작성 시 작성자는 검증된 사용자 ID로 서버에서 지정합니다. 요청 본문에는 제목과 본문만 허용하고, `authorId`나 `userId`를 추가하면 `400 BAD_INPUT`으로 거부해 작성자 위조를 막았습니다.

### 401과 403에 맞춰 화면 상태 연결하기

공통 `request()` 함수가 401을 받으면 `clearSession()`으로 토큰과 사용자 정보를 지우고, 화면도 로그아웃 상태로 갱신합니다. 403에서는 권한 부족 안내를 표시하면서 로그인 상태를 유지합니다.

토큰은 `localStorage`나 `sessionStorage`에 저장하지 않습니다. 새로고침하면 로그인 정보가 초기화되고, DB에 저장한 게시글은 유지됩니다. 토큰 만료는 보호 요청 시 확인하며, 로그아웃으로 이미 복사된 토큰이 서버에서 무효화되는 구조는 아닙니다. 해당 토큰은 만료 전까지 사용할 수 있습니다.

## 검증 결과

아래 결과는 **2026년 10월 구현 보고서에 기록한 검사와 화면 캡처 기준**입니다.

| 검증 항목 | 결과 |
| --- | --- |
| 일반 API 자동 검사 | **78개 항목 모두 통과** |
| 만료 시나리오를 포함한 자동 검사 | **총 86개 항목 모두 통과** |
| 다른 작성자의 수정·삭제 | Bob이 Alice의 글을 변경하려 하면 403, 재조회 시 원문 유지 |
| 토큰 변조·만료 | 내 정보 조회와 등록·수정·삭제를 각각 401로 거부, 기존 데이터 유지 |
| 인증과 게시글 존재 확인 순서 | 토큰 없이 없는 글 수정 시 401, 정상 토큰으로 요청 시 404 |
| SQLite 영속성 | 서버 재시작 후 동일 게시글의 내용·작성자·시각 유지 |
| 프론트 빌드 결과 | 로컬 4173번 포트에서 비로그인 목록 조회 200 OK 확인 |

만료 검사는 `TOKEN_TTL=3`으로 서버를 실행하고 토큰 발급 후 4초를 기다리는 조건에서 수행했습니다. 만료된 토큰의 내 정보 조회와 게시글 변경 요청이 모두 `401 TOKEN_EXPIRED`로 거부되고, 임시 검사 게시글이 정상 삭제되는 것을 확인했습니다.

## 어려웠던 점과 해결 과정

가장 어려웠던 부분은 토큰 만료 후 **서버의 인증 결과, 메모리의 사용자 정보, 화면의 로그인 표시를 함께 맞추는 것**이었습니다. 오류만 전달하면 메모리에 토큰과 사용자 정보가 남을 수 있어 API 요청 처리와 화면 갱신 흐름을 함께 살폈습니다.

`request()`의 401 처리에서 세션을 초기화하고, `App.vue`의 `run()`에서 사용자 정보를 다시 읽는 흐름과 연결했습니다. 짧은 TTL로 만료를 재현한 뒤 내 정보 조회를 요청해, 만료 안내와 함께 로그아웃 버튼이 사라지는 것을 확인했습니다. 반대로 타인의 글 변경이 거부되는 403에서는 로그인 상태가 유지되는지도 점검했습니다.

이 과정을 통해 인증 기능은 토큰 발급에서 끝나지 않으며, 요청 실패 이후의 화면 상태와 데이터가 유지되는지까지 확인해야 한다는 점을 배웠습니다.

## 남은 개선 과제

현재 서비스는 제목과 본문으로 맛집 정보를 공유하고 Alice·Bob 테스트 계정으로 인증을 확인하는 로컬 실행 과제입니다. 다음 단계로 게시글을 읽고 쓰기 편하도록 화면과 버튼 배치를 개선하고, 음식 사진을 첨부하는 기능을 추가하고자 합니다.
